# 制作约定与旧版复盘

## 本轮已经授权的范围

建立可快速接手的纯蓝图基础、精简目录、蓝图滚球和可移动相机、专用实验关卡、学习与交付说明、验证和 GitHub 阶段提交。基础整理直接执行。玩法创新、最终美术方向、关键效果完成方式以及会覆盖本人作品的修改，先给出具体可审阅结果。

当前方向：小范围雨后自然庭园、植被适量、球与环境相互影响。每周可投入 3 天；截止日期和每天工时尚未确认，不编造排期。最终作品面向特效向 TA，重点是交互、材质、Niagara、美术表现和性能解释能力。

## 旧版的经验与改进

| 旧版问题 | 新版做法 | 怎样判断改进有效 |
| --- | --- | --- |
| 玩法主要写在 C++，本人无法从节点接手 | 自写玩法使用蓝图，功能分成短事件和函数，并提供中文说明 | 能在编辑器找到入口、修改参数、解释执行顺序 |
| 一次交付很多框架，缺少直观成果 | 每个阶段提供可以打开、试玩、修改的最小成果 | 进度页给出准确关卡和资产位置 |
| “参考教程”和“照着能完成的教程”混在一起 | 每个链接写清用途、跟做到哪里、如何接入本项目 | 不要求本人自行把雪地教程改成球体系统 |
| 动态状态基础被误认为最终效果 | 分别记录数据、图表编译、运行行为和视觉结果 | 每一层都有独立状态，不用代码通过代替成品验证 |
| 功能做完但没有推送到 GitHub | 区分本地提交与远程推送，验证提交号一致 | 阶段日志记录提交号、仓库和未通过项目 |
| 文档和目录太多，难以找到入口 | 根目录 README 和一个进度入口；按功能少量分类 | 日常从 OpenProject.cmd、Progress.md 两处接手 |
| 自动生成或重做可能覆盖作者成果 | 修改前读取资产；试验先在独立关卡进行 | 不覆盖 Student 资产，不重建整张作者地图 |
| 过早添加许多候选特效 | 先验证一个完整沾染过程，再决定扩展 | 新效果要能说明用途、成本、学习收益 |

旧版已积累的接触思路、输入排错和性能验证方法可参考；旧版 C++ 类型与局部 CPU 状态场不迁入新工程。旧版性能数字不作为新版或最终效果的性能结论。

## 目录和命名

资源统一放在 `Game`、`Student`、`ThirdParty` 三个内容根目录。`Game` 按 Core、Player、World、Effects、Maps、UI 分类；同一功能的材质、纹理和 Niagara 可以放在一起，不必再按所有资产类型层层拆分。

| 前缀 | 用途 | 例子 |
| --- | --- | --- |
| `BP_` | 蓝图类 | `BP_RollingBall` |
| `L_` | 关卡 | `L_InteractionLab` |
| `M_` / `MI_` | 材质 / 材质实例 | `M_BallSurface` |
| `T_` / `RT_` | 纹理 / 渲染目标 | `RT_BallDirt` |
| `NS_` | Niagara 系统 | `NS_MudSplash` |
| `IA_` / `IMC_` | 增强输入动作 / 映射 | `IA_Move` |
| `WBP_` | 控件蓝图 | `WBP_PlayHint` |

目录和资产名称使用英文。蓝图注释、提示、文档可以使用中文。按功能加说明，例如“移动：相机方向决定前后”，不只写“逻辑1”。避免 `Final2`、`NewNew` 等临时名称。

## 分工：哪些留给本人

本人负责关键效果的实际制作与理解、材质和 Niagara 参数调整、美术判断、玩法原型选择、观察测试和记录反思。AI 不应把关键学习任务全部代做后只留下调参。

AI 可以直接完成重复性的目录、基础蓝图骨架、工程设置、资源依赖检查、素材来源整理、调试工具、验证和版本管理。涉及本人学习目标的功能，交付时必须说明：打开哪个资产、从哪个事件开始、改变哪个参数、应该出现什么现象。

辅助工具用 Python 与官方 MCP 编辑资产，不代表游戏用 Python 实现。游戏行为必须保存为能在 UE 中查看的蓝图节点，运行时不依赖辅助脚本。

## 制作路线与验收

| 阶段 | 交付结果 | 本人需要掌握 |
| --- | --- | --- |
| 起步 | 可启动实验关卡、能控制的蓝图球、可绕球观察的相机、重置 | 输入、物理组件、相机组件与事件入口 |
| 沾染原型 | 局部痕迹跟球转，接触泥地自动累积 | 球面局部位置、状态保存、接触输入 |
| 清洗原型 | 接触水时局部变湿并逐渐洗净 | 泥量与湿润分开，局部接触与渐变 |
| 正式效果 | 泥斑边缘、湿润反光、少量 Niagara 泥水飞溅 | 材质层次、粒子生命周期、参数驱动 |
| 短玩法 | 有起点、一次学习、一次变化、一个结束的可玩段落 | 玩家目标、反馈、路线和节奏；先审阅再扩展 |
| 完成 | 正式环境、音效、必要 UI、可打包版本、作品展示与论文证据 | 性能取舍、测试、缺陷修复、讲解自己的作品 |

首先验证：小斑点跟球转动、球自动留下局部泥痕、部分接触水只清洗对应位置。这些成立之后再做好看的泥材质。固定 SphereMask 只能验证坐标，不能充当已经保存的沾染记录。

不把虫群、藤蔓、Morph 等候选同时加入排期。是否加入需要回答：让玩家做什么新的选择？是否值得额外制作成本？是否能成为解释清楚的 TA 作品？

## 阶段提交规则

使用现有 GitHub 仓库，不切换 Bitbucket。基础目录和小修复可直接提交；一个较大的新功能完成后，先验证，再推送。不要等待最终毕业作品完成才备份。

阶段检查：蓝图编译、实际运行、视觉观察、作者能否接手、依赖和 Git 内容。记录未测或失败项，不用“全部通过”遮盖缺口。代码或图表通过，不代表手感、美术已经通过。

资产使用 Git LFS；提交 Config、Content、必要工具和说明，排除缓存、构建产物、用户设置与本地 MCP 会话。不强推，不覆盖远程历史，不在未完成时打正式版本标签。推送后核对本地与远程提交号。

常用流程：`git status` → 查看差异 → 提交相关文件 → `git push`。AI 获得持续阶段推送授权；新增付费资源、公开发布个人资料、改仓库可见性不在此授权内。
